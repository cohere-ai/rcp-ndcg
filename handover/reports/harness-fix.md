## What changed

**The port onto the family layout (`c217883d`).** rfam's recipe line landed 97 commits (15 family
directories, one test module per family, per-variant goldens + `DELTAS.json`, the pairs manifest, plus
rec-overrides, sz-misc, rec-egemma2, rec-harrier and the l10b/mrl-core/rf-engine/sync-hardening/
scoring-fixes merges).  The port resolved the conflicts as follows: the per-recipe test modules rfam
deleted stay deleted, and the lane's schema pins (`"device": None`, `"step_budget_s": None`) moved into
the family modules' contract mappings; the goldens and `DELTAS.json` were regenerated the documented way
(`pytest .../test_family_goldens.py --update-goldens`; the regenerated snapshot now resolves exactly, so
the deltas shrank to none); `recipe.schema.json` and `family.schema.json` were regenerated from the
merged models; the pairs manifest and all pairs files were regenerated with the fixed planner for the
merged catalog (27 variants, including the new harrier/gemma/octen/jina-nano/topk-xsmall files); the wave
list `all-retrieval.txt` was regenerated (27 ids); the staging keeps the wheel-based `stage_tree`
(rfam's regression test was updated to guard the package-data source path under it); the planner keeps
the role-aware empty policy and the over-cap row for every role (rfam's dead `elif` branch dropped); the
docs keep both sides' family text and the current job paths; the CHANGELOG keeps both sides' entries.
The recipe network suite is fully green (0 baseline failures; the 34 recorded pre-port failures are
fixed by the family modules).

**1. One stuck request no longer holds the node.** Each ready recipe's steps run in a worker thread of
their own (`_Worker`); every step has a declared wall-clock budget (`_step_budget_s`: base 600 s plus
60 s per request from the recipe's pairs row count, raised by `engine.step_budget_s`). The budget is
enforced cooperatively at the request seams (`stepwatch.StepWatch`: the capturing transport bounds each
send with `asyncio.wait_for(remaining)` and cancels the in-flight request at the edge) and by the step
executor (a body the watch cannot reach is abandoned after a 30 s grace). An overrunning step fails with
exactly `step <name> exceeded <budget>s; in flight: <method path, request index>`, stops that engine, and
the other recipes continue. A step the executor abandons never accepts a late pass.

**2. Partial results.** `status.json` is rewritten atomically (`rcp_ndcg.storage.publish_bytes`, R30)
after every step, and with `--upload` each finished recipe's directory is copied the moment the recipe
ends (`_upload_recipe`); `wave.json`/`WAVE.md` still land at the end.

**3. The pod log.** One line per step boundary per recipe, `run_wave: <recipe> <step> start|passed|failed
<secs>s`; the serve step gets `serve start` at engine start and `serve passed|failed <secs>s` at the end,
with its running state written to disk at start. No request bodies, no environment values.

**4. An engine's death fails only its recipe.** Engines already ran in their own session/process group
(`start_new_session`); the runner now fails the recipe's `serve` step the moment the engine dies (the
step executor checks liveness while joining), with the engine's last log lines in `serve.log` and a
clipped tail in the step document. A runner-initiated stop is not a death. Tests: the stub's new
`--fault abort|hang [--fault-only <model>]` mode (SIGABRT mid-run; a stuck request), plus the wave's
end-of-wave sweep: a live-engine registry and a closing flag guarantee no engine outlives the wave.

**5. PEP 508 markers.** `reference_deps.py` evaluates each requirement's full marker with
`packaging.markers` against the reference interpreter (no extra), with a local evaluator for the common
environment markers when `packaging` is absent. The `tomli; python_version < "3.11"` case is not planned
on 3.12.

**6. rc_build.sh builds and stages exactly what ships.** `build_published` builds the three published
distributions by name (one `--package` per invocation, as release.yml; the unpublished workspace member
is never swept in). `check_pins` asserts `rcp-ndcg` pins `rcp-ndcg-core==<version>` and that the lean
`rcp-ndcg-vllm` manifest names NO workspace sibling (decision 18). `stage_tree` stages the recipes from
the BUILT wheel's package data (never a per-recipe list; a missing package-data directory fails the
build), the pairs files from `rcp-ndcg-test/pairs/`, the committed wave lists from
`rcp-ndcg-test/wave-lists/`, and the `EXTRA_DIRS` entries; a real-checkout test guards every path. The
requirements-reference staging carries a marked REF-ENVS SEAM (decision 35) and was not redesigned. The
committed `all-retrieval.txt` is generated by `python -m rcp_ndcg_test.jobs.wavelist` from
`iter_recipes()` and pinned to it by a test.

**7. Every reference runs on a GPU of its own.** The packing reserves one GPU per recipe whose reference
is a subprocess and whose declared device is not `cpu` (8 GPUs: at most 4 single-GPU recipes), pins the
reference subprocess with `CUDA_VISIBLE_DEVICES`, and records `device`/`reference_gpu` in
`equivalence.json` (and in the step document). A recipe declaring `reference.device: cuda` refuses a CPU
run with the way out (early, if the pod cannot spare the GPU); `device: cpu` reserves none and the
controls' gates run the reference on the recipe's own device. The harness's own requests (smoke, record,
the corpus's bare probes) run with the declared `_REQUEST_TIMEOUT_S = 120 s`, shorter than every step
budget and reported in the step documents.

**8. The planner's over-cap row follows any declared deviation, every role** (operator addendum; the
over-cap stratum was absent with a false reason for the embed recipes and the rerankers declaring
`over_cap_cut_differs`). All pairs files were regenerated the generator's own way, which also surfaced
and fixed a second, pre-existing planner bug: eight `getattr(recipe.client, ...)` reads on a plain dict
returned fallbacks (the empty-content row was dropped for recipes that send the empty string,
`query_max_tokens` read 0, the instruction mode read `none`). The query-side empty policy is role-aware
(`empty_query` is rerank-only; the embed/pooling roles' `empty_doc` governs both sides). `GENERATOR_VERSION`
stays 1 by declared rule: it also seeds the sampling, so a bump would re-draw every recipe's rows for a
bug fix; the docstring states this and the manifest's per-file SHA-256 pins the artifact.

## Open questions

- **`GENERATOR_VERSION`**: the version doubles as the sampling seed, so the fix that changed the
  generator's output did not bump it (documented at `requests.py`'s constant). If the owner wants the
  named generator identity to move with the artifact, the clean change is to separate the sampling seed
  from the semantic version — which itself re-draws every row; that was deliberately avoided here.
- **The family goldens' `DELTAS.json` is now empty**: the regeneration (required by the new schema
  fields) rewrote the snapshot to the family tree's exact resolved values, so the recorded
  `client.listwise`/`client.request_shape` deltas are gone.  That is the documented regeneration; a
  reviewer may want to confirm the shrink is intended.
- **`all-retrieval.txt` now lists 27 variants** (the merged catalog, including harrier, gemma, the new
  octen sizes, jina-nano and topk-xsmall); regenerate it after any catalog change with
  `python -m rcp_ndcg_test.jobs.wavelist --out rcp-ndcg-test/wave-lists`.
- **Residual race**: an abandoned corpus body can still start an engine after its worker's snapshot;
  the closing flag refuses late starts and the wave's sweep stops whatever is live, so the leak is
  closed at the wave's end, but a late start between the snapshot and the close is refused loudly rather
  than drained.
- **rec-harrier's `bd6f210f`** (not on rfc-0001) fixes the same dict reads for the family layout;
  the merge will take either side of the same `.get()` change.
