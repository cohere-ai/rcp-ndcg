## 3. The backend evidence table (embeddinggemma-2)

The pinned image is `vllm/vllm-openai:nightly-8cbd5d03006c33185f402249ff2b448efd594986@sha256:b25e8a04...`; the
r4 evidence established that its vLLM core is the v0.31.0 tag's (the serve log's architecture list is exactly
the tag's, and its Gemma4 hook behaves as the tag's does). The model's head dims are heterogeneous: sliding
256, full 512.

| backend | outcome | exact evidence |
|---|---|---|
| `TRITON_ATTN` | rejected — the prefill kernel cannot compile for head_dim 512 | `triton.runtime.errors.OutOfResources: out of resource: shared memory, Required: 266240, Hardware limit: 232448` at `triton_prefill_attention.py`'s `context_attention_fwd`, inside `compile_or_warm_up_model` (the round-7 serve log). The tile is fixed: `get_block_size(bf16)` is 128 on SM10x, and `BLOCK_N` is narrowed to 32 only on RDNA (`_prefer_narrow_kv_tile()` is ROCm-only), so no flag moves the demand. |
| `FLASH_ATTN` (FA4) | rejected — the FA4 kernel caps the head dim | `FlashAttention forward only supports head dimension at most 256` from `mha_varlen_fwd`, for the full-attention layers' head_dim 512 (the round-8 wave). The image's Gemma4 hook selects FA4 itself (`... heterogeneous head dimensions ... Using FA4 for all layers`), which is why the round-7 pin got as far as model load. |
| `TORCH_SDPA` | refused at backend selection — not a decoder backend on this image | In the v0.31.0 tag the image is built from: `TORCH_SDPA = ""  # this tag is only used for ViT`. The manual-selection path calls `AttentionBackendEnum.get_class()` -> `get_path()`, which raises `ValueError: Backend TORCH_SDPA must be registered before use. Use register_backend(Backend.TORCH_SDPA, 'your.module.YourClass')`; `CudaPlatform.get_attn_backend_cls` wraps only `ImportError`/`OSError`, so the `ValueError` propagates at startup. (Deterministic source evidence; no GPU run needed.) |
| `FLEX_ATTENTION` | **chosen** | `vllm.v1.attention.backends.flex_attention.FlexAttentionBackend` is registered and is in the CUDA platform's own decoder backend list. It passes the static selection validation for this model: `get_supported_head_sizes()` is empty (no cap), bf16 is supported, the kernel block size is a `MultipleOf(16)` (the default 16), `supports_attn_type` includes `ENCODER_ONLY` (the vendored `embedding_gemma2.py` passes `AttentionType.ENCODER_ONLY`), and `supports_sliding_window`, `supports_non_causal` and `supports_mm_prefix` are all true. Both config hooks leave a requested backend alone: the folded EmbeddingGemma2 hook only defaults when none was requested, and the image's Gemma4 hook forces FA4 only for a `None` or `FLASH_ATTN` backend. |

Fallback order and the one dead end: TORCH_SDPA (refused) -> FLEX_ATTENTION (chosen) -> the smallest Triton
block (not reachable by configuration on CUDA: the tile is derived from the dtype and the device capability,
not from a flag). The wave's T0 model load is the confirmation; the flag is removed together with the fold when
the engine image moves to a release whose registry carries the model.

## 4. The patched symbol (topk-embed-v1)

- **Patched:** `transformers.models.qwen3_5.modeling_qwen3_5.Qwen3_5TextRotaryEmbedding.forward` (5.17.0;
  the class is at line 143, its `forward` at line 178).
- **Why that class:** `Qwen3_5TextModel.__init__` assigns `self.rotary_emb = Qwen3_5TextRotaryEmbedding(
  config=config)` (`modeling_qwen3_5.py:1232`), and the remote `PackedQwen3_5TextModel.forward`
  (`hf_backbone.py`) calls `self.rotary_emb(inputs_embeds, position_ids)` with the feature's
  `position_ids`. The remote wrapper's text branch builds those 2-D (`topk_embed_st.py._position_ids`:
  `within.unsqueeze(0)`, shape `(1, total)`).
- **Failure it prevents:** `IndexError: too many indices for tensor of dimension 2` at
  `modeling_qwen3_5.py:192` (`position_ids_expanded = position_ids[:, :, None, :].float()`) for every
  text-only embed — the r4 and r8 waves.
- **Why round 7 missed:** it patched `Qwen3_5RotaryEmbedding`, a name that exists in no transformers release
  (5.9.0 and 5.17.0 both carry `Qwen3_5TextRotaryEmbedding`), inside a `try/except ImportError: return`, so
  the miss was silent. The CPU test injected its class through the `rope_cls` seam and never exercised the
  resolution.
- **What the shim restores:** transformers 5.9.0's own 2-D branch —
  `position_ids = position_ids[None, ...].expand(3, position_ids.shape[0], -1)` — as a wrapper that promotes a
  2-D input to `(3, bs, positions)` and passes a 3-D input through. The class is resolved from the module
  (`importlib.import_module`), and a module that exists without the class raises a `RuntimeError` naming it.

## CHANGELOG entry

Inside the one `## 0.0.1` section, `### Fixed` (the two round-7 bullets rewritten to the shipped behaviour):

- **The topk-embed-v1 reference restores the 2-D rope branch on the class the remote code calls** (the E2
  rounds 7-8 reference crash): the wrapper's text branch builds 2-D rope positions (`within.unsqueeze(0)`),
  which the checkpoint's own transformers 5.9.0 promotes inside `Qwen3_5TextRotaryEmbedding.forward`;
  transformers 5.17 removed that branch and reads only the 3-D mrope form (`position_ids[:, :, None, :]`), so
  every text-only embed died with `IndexError: too many indices for tensor of dimension 2`. The declared shim
  wraps `Qwen3_5TextRotaryEmbedding` — the class `Qwen3_5TextModel.__init__` assigns to `self.rotary_emb`,
  which the remote `PackedQwen3_5TextModel.forward` calls — promotes a 2-D input to `(3, bs, positions)`,
  exactly 5.9.0's own promotion, and leaves a 3-D input untouched. Round 7's version imported a
  `Qwen3_5RotaryEmbedding` that no transformers release defines and swallowed the ImportError, so it never
  wrapped anything; the shim now resolves the class from the module and raises loudly when the module exists
  without it. CPU tests pin the wrapper, the symbol resolution and the loud miss.
- **The embeddinggemma-2 engine runs on FLEX_ATTENTION** (the E2 rounds 7-8 backend search): the model's
  heterogeneous head dimensions (sliding 256, full 512) leave no default backend — TRITON_ATTN's prefill kernel
  needs 266240 B of shared memory against the 232448 B limit, and FA4's kernel rejects head_dim 512
  (`FlashAttention forward only supports head dimension at most 256`) — while TORCH_SDPA is not a decoder
  backend on the v0.31.0-based image (its enum value is empty: "this tag is only used for ViT", so the
  manual-selection path raises `Backend TORCH_SDPA must be registered before use`). The recipe pins
  `--attention-backend FLEX_ATTENTION` (no head-size cap; encoder-only, sliding-window, non-causal and
  image-token attention all supported); neither `--enforce-eager` nor `--max-num-batched-tokens` changes a
  compile-time demand, and the Triton tile is not configurable on CUDA. The recipe notes record the fallback
  order and each rejected backend's error; a CPU test pins the argv.
