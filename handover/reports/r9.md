## 4. The reference API evidence (topk-embed-v1-small/-xsmall)

**The missing method.** The checkpoint's `hf_backbone.py:111` (a `Qwen3_5GatedDeltaNet` subclass that swaps
itself onto the layer) calls `self.chunk_gated_delta_rule(query, key, value, g=..., beta=...,
initial_state=None, output_final_state=False, use_qk_l2norm_in_kernel=True, cu_seqlens=cu_seqlens)`.

- transformers **5.9.0** (the checkpoint's own `requirements.txt` pin): `modeling_qwen3_5.py:422`
  `self.chunk_gated_delta_rule = chunk_gated_delta_rule or torch_chunk_gated_delta_rule` — an **instance
  attribute assigned in `__init__`** — and its own forward calls it at `:535`. The `chunk_gated_delta_rule`
  name resolves to flash-linear-attention's kernel when `fla` is installed (the family pins
  `flash-linear-attention==0.5.1`), which is what makes the packed `cu_seqlens` path correct.
- transformers **5.10.4**: the attribute is still there (line 422, byte-checked).
- transformers **5.16.0** and **5.17.0**: the attribute is gone; the class's forward calls the module-level
  `torch_chunk_gated_delta_rule` directly (`5.17.0` `modeling_qwen3_5.py:639`). That function's signature is
  `(query, key, value, g, beta, chunk_size=64, initial_state=None, output_final_state=False,
  use_qk_l2norm_in_kernel=False, **kwargs)`, and its body contains **zero** occurrences of `cu_seqlens` —
  the remote code's packed-document argument is accepted by `**kwargs` and ignored. Delegating the missing
  call to it would silently change the reference's packed-document numerics, so no shim was written.

**Why the pin is the honest fix (and why the earlier rationale no longer holds).** `reference.in` said the
range `>=5.10.4,<5.18.0` was chosen so "the reference runs on the image's transformers stack ... instead of a
5.9.0 that the node's constraint install cannot replace the image's with". That rationale does not hold for
this family:

- it declares `# own-torch: true`, so `jobs/bootstrap.sh` builds its reference venv **without**
  `--system-site-packages` and installs exactly the lock's pins — the image's transformers is never visible;
- `jobs/reference_lock.py`'s own contract (decision 35) says every non-stack family pin "installs **into** the
  venv and takes precedence over the image's copy — that is the decision's whole point: one recipe's
  transformers pin (e.g. a checkpoint's remote code needing an older release) can no longer break the wave";
- the family is one environment per family, so the pin cannot affect another recipe's wave.

**The regenerated lock.** `python -m rcp_ndcg_test.jobs.reference_lock build --family topk-embed-v1 ...` (the
documented tool, run with the extra index variable unset so PyPI is the index) resolves:

- `transformers==5.9.0` (was `5.17.0`);
- `tokenizers==0.22.2` (was `0.23.3`): 5.9.0's own METADATA declares `tokenizers<=0.23.0,>=0.22.0`, and
  0.23.0 was never published, so the newest release the range allows is 0.22.2; the declared spec is
  `tokenizers>=0.22.0,<=0.23.0`;
- everything else unchanged (`torch==2.11.0`, the CUDA stack, `sentence-transformers==6.0.1`,
  `flash-linear-attention==0.5.1`, `kernels==0.14.1`, `safetensors==0.8.0`, `huggingface-hub==1.33.0`, ...).

`reference_lock check` passes on the committed lock, and the lock's SHA-256 (the environment identity the
stored reference outputs key on) changed, so the next wave recomputes the family's stored reference outputs —
expected for a deliberate environment change.

**The pin does not break the other modes (checked on CPU).** The other pins are compatible with 5.9.0:
sentence-transformers 6.0.1 declares `transformers<6.0.0,>=5.0.0` and `tokenizers>=0.19`,
flash-linear-attention 0.5.1 declares `transformers>=4.45.0`, and 5.9.0's own
`huggingface-hub<2.0,>=1.5.0` covers the pinned 1.33.0. Render mode (which needs only `huggingface_hub` and
`tokenizers`) was run against the real pinned checkpoint under **tokenizers 0.22.2** and under the dev
environment's 0.23.2, on three sample rows and on over-cap rows (a 5,417-character query cut at 1,024 tokens
and a 38,723-character document cut at 8,192): the two outputs are **byte-identical** (`diff` empty), so the
cut path (`no_truncation`, `enable_truncation(strategy="longest_first", direction="right")`, offsets) behaves
identically on the pinned release. Media mode needs no transformers at all.

**The declared shims.** `_alias_qwen3_5_layer_type` and `_promote_qwen3_5_rope_position_ids` remain in

## 5. The corpus check (item 3)

- **Where:** `rcp_ndcg_test.observe.corpus._numbers` (the `scores_finite_and_vector_widths` check).
- **Before:** the recipe's `declared_dim` was the expected width of every decoded vector, and one width was
  tracked per request path. The plan's MRL stratum (`observe/requests.py::_wire_variants`) sends one bare
  `dimensions=k` probe per declared `k`, and the stub engine (and vLLM) slices the reply to `k` — so the
  probe's `k`-wide reply was compared against the full declared width, and the route's first width (1,024)
  disagreed with every later probe width (the r3 wave's exact message).
- **After:** `_requested_dimensions(record)` reads an integer `dimensions` from the record's request body; a
  row carrying one is checked at that requested `k`, a row without one at the declared width (when the
  manifest records one). The per-route width map is keyed by `(path, requested_dimensions)`, so the
  full-width rows beside a probe no longer disagree. A reply at neither the requested nor the declared width
  still fails, and the mismatch names the width it should have been.
- **Scope:** the check is harness-side only; no recipe, plan or engine behaviour changed. The
  `schema/observation-corpus.md` description and the `verify_corpus` docstring were updated in the same
  commit.
