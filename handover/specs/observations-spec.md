# Observation corpora: what the GPU waves collect, how, and with what provenance

Binding for lane `gpu-quality` (the collector, on the GPU node) and lane `fake-engines` (the consumer, CPU only).
Purpose: corpora from which verified fake engines are built, verified, re-verified and diffed for years, across new
checkpoints, templates, pooler settings, plugins and engine versions, without ever being silently stale.

## Principles
1. **Raw first, interpretation later.** Store exactly what crossed the wire (request bytes as sent, response bytes as
   received, headers that matter). Every derived view (parsed JSON, normalised bodies, decoded vectors, tolerances) is
   recomputed from the raw record by versioned code, so a later change of normalisation or decoding never needs a
   re-recording.
2. **Same questions, every time.** The request set is generated by a deterministic, versioned generator from pinned
   inputs (dataset commits, a seed, a synthetic adversarial set stored as text). Re-recording a new implementation asks
   exactly the same questions, so behaviour diffs are input by input.
3. **Two layers.** Protocol behaviour (per engine and version) and model behaviour (per recipe behaviour fingerprint) are
   collected and stored separately (GPU-VALIDATION.md item 8).
4. **Provenance complete enough to explain any difference later**, and hash-chained so nothing can be edited unnoticed.
5. **Measured, not assumed, non-determinism.** The tolerances an emulator is verified with come from repeated
   measurements, stored with the corpus.

## 1. The request set (generator `rcp_ndcg_vllm.observe.requests`, versioned `GENERATOR_VERSION`)
Per recipe, deterministic from (`GENERATOR_VERSION`, seed, dataset URIs at pinned commits, the recipe's role and
shapes). Strata, each with a minimum count and recorded as present or absent (absent only when inapplicable, said why):
- **Shapes**: every request shape the recipe declares (`query`, `document`, `pair`), and each instruction mode it uses.
- **Lengths** in the recipe's own tokens: tiny (1-8), short, median of the source data, at 90-100% of the budget, exactly
  at the budget, 1 token over, 2x over, 10x over (the over-length ones exercise both the client cut and, sent uncut on
  purpose, the engine's own refusal).
- **Content kinds**: ASCII prose, code, CJK, Arabic or Hebrew (right-to-left), emoji and ZWJ sequences, combining marks,
  whitespace-only, the empty string, very long single tokens (URLs, base64 blobs), text containing the model's special
  tokens' literal spellings (to see whether the engine treats them as specials).
- **Media** (vision-language recipes): no image, one image per size bucket (tiny, icon, A4 at 72/150/300 dpi, 16:9 slide,
  very tall receipt, extreme aspect), several images up to and over the media limit, a short video at the pinned frame
  count, a corrupt image.
- **Sources**: real items sampled from the suites (NanoBEIR, BRIGHT for long documents, ViDoRe v3 for pages, TREC DL), by
  id at their commits, plus the synthetic adversarial set; the selection manifest lists every source id.
- **Wire variants**: every route the role uses and every encoding (`float`, `base64`, `bytes` for `/pooling`; `top_n`
  variants for `/rerank`), the request fields the adapters can send (`dimensions`, `use_activation`, `instruction`,
  `embed_dtype`) each on and off.
- **Errors and edges** (protocol layer, collected once per engine version with the smallest recipe of each role): unknown
  request field, invalid `embed_dtype`, over-length, too many images, malformed JSON, wrong model name, empty `input`,
  `top_n` larger than the documents, a request while the engine is still loading (readiness), and the `/v1/models` and
  health responses.
- **The engine's tokenization**: for every sampled input, the engine's own `/tokenize` reply for the exact prompt or
  messages the client sends (the ids and the count), recorded as ground truth for the client's `fit()` and for the fake
  engines' token counting.
- **Batching**: each sampled input sent alone and inside batches of 2, 8 and 32 with different companions (bf16 kernels
  can change numbers with batch composition), and the rerank candidate set in two orders.

## 2. Repetition and non-determinism
Every request is sent **twice in the same server process**, and the whole set once more **after an engine restart**.
Stored per input and per batch context: the maximum absolute and relative differences (scores, vectors per component,
cosine per vector or token), and whether statuses or bodies differ at all. The emulator's verification tolerance for a
recipe is derived from these numbers (stored, with the rule that derived them), never chosen by hand.

## 3. The record of one exchange (JSON Lines, one object per exchange; `RECORD_SCHEMA = 1`)
- `exchange_id` (content address: SHA-256 of the canonical request), `sequence` (order sent), `repetition`
  (`same_process` 1 or 2, `after_restart`), `batch_context` (the companion request ids and positions), `server_run_id`.
- `request`: method, path, the headers that matter (content type; **never** authorisation or gateway headers — they are
  stripped before writing and a test scans every corpus for credential-shaped strings), the body **as sent** (bytes,
  base64 when not UTF-8) and its parsed form.
- `response`: status, the headers that matter (content type, server, any version header), the body **as received** (raw
  bytes, base64 for binary encodings, plus the parsed JSON when it is JSON), `latency_s` (recorded, never used for
  verification).
- `inputs`: what the generator meant — source dataset, id, commit, stratum labels, the token count of each content span
  in the recipe's tokenizer, the declared media.
- `derived` is **not stored**: parsed vectors, normalised bodies and tolerances are recomputed on load by versioned code
  (`NORMALISATION_VERSION` names the volatile fields it strips, such as request ids and `created` timestamps).

## 4. Provenance (`manifest.json` per corpus; hash-chained)
- **Engine**: image reference **and digest** (`sha256:...`), vLLM version and git commit as the installed package reports
  them, torch, CUDA and driver versions, GPU model and count (`nvidia-smi --query-gpu`), the exact serve argv executed,
  the engine environment variables that affect behaviour (`VLLM_*`, without secrets), engine start time and the
  readiness wait.
- **Model**: model id, revision, the SHA-256 of every weight file's index (or of each file), the tokenizer's
  `tokenizer.json` SHA-256, the template file's SHA-256, the plugin package name, version and wheel SHA-256 (out-of-tree
  models), `hf_overrides`, pooler config, `mm_processor_kwargs`, dtype.
- **Recipe**: recipe id, the recipe file's SHA-256, the **behaviour fingerprint** and the full list of its inputs with
  their values (so a staleness failure can name what changed), the recipe's `status` at recording time.
- **Collector**: `rcp-ndcg-vllm` version and git commit, `GENERATOR_VERSION`, `RECORD_SCHEMA`, seed, dataset URIs and
  commits, the wave id, the job id, start and end times, the node's hostname **hashed** (never the plain name).
- **Integrity**: the SHA-256 of every corpus file, and the manifest's own SHA-256 recorded in the repository's corpus
  index; the conformance suite refuses a corpus whose files do not hash to the manifest.
- **Verification record** (written by `fake-engines`, appended, never rewritten): which emulator version verified the
  corpus, when, with which tolerances, and the result.

## 5. Storage
- **Full corpus** on GCS under an immutable, versioned path:
  `<results-prefix>/observations/<engine>-<version>/<recipe>/<fingerprint>/<recorded-at>/` (never overwritten; a new
  recording is a new path).
- **Repository subset** under `tests/contract/engines/<engine>-<version>/<recipe>/<fingerprint>/`: a stratified sample that
  covers every stratum, compressed JSONL, vectors as the exact received bytes (or float16 `.npy` when received as float
  lists), at most 2 MB per recipe and 30 MB in total, plus the manifest and an `index.json` naming the GCS path and hash
  of the full corpus it was sampled from (the sampling is deterministic and recorded).

## 6. Checks on every corpus before it is accepted
Completeness against the generator's plan (every stratum present or explained); every status as expected (refusals
where the engine must refuse); every score finite, every vector the declared width and dtype; the non-determinism
report present; no credential-shaped string anywhere; manifest hashes valid; the equivalence harness's results for the
same wave consistent with the corpus (the same served replies). A corpus failing any check is not used.

## 7. Change handling
- **Re-record changed only**: the wave runner's `--changed-since <corpus-index>` mode recomputes every recipe's
  fingerprint and records only those that differ (and, for a new engine version, the protocol layer once).
- **Behaviour diff** (written by `fake-engines` from two corpora of one recipe): per input, the score or vector deltas,
  changed statuses, changed refusals and changed protocol behaviour, summarised by stratum; reviewed before the new
  corpus replaces the old in the repository, and judged with the same equivalence gates.
- **Schema evolution**: readers support every `RECORD_SCHEMA` they ever wrote (migrations in code, tested on a frozen
  sample of each old schema); a schema bump never invalidates an old corpus.
- **Retirement**: an old corpus leaves the repository only by a deliberate commit that names it; its GCS copy stays.
