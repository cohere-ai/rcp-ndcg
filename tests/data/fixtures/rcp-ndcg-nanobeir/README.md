# RCP-nDCG · NanoBEIR (MTEB-style, with continuous relevance gains)

**Evaluate with stock [mteb](https://github.com/embeddings-benchmark/mteb) (≥ 2.0.1). No fork is
needed.** This repo ships `rcp_ndcg_tasks.py`. It defines one mteb task per subset (13 tasks, e.g. `NanoArguAnaRCPReranking`),
which reports the continuous-gain metric `ndcg_float_at_10` alongside mteb's usual metrics:

```python
import importlib.util
import mteb
from huggingface_hub import hf_hub_download

path = hf_hub_download("fabianschmidt-cohere/rcp-ndcg-nanobeir", "rcp_ndcg_tasks.py", repo_type="dataset")
spec = importlib.util.spec_from_file_location("rcp_ndcg_tasks", path)
rcp = importlib.util.module_from_spec(spec)
spec.loader.exec_module(rcp)

tasks = rcp.get_tasks()                        # all subsets; or rcp.get_tasks(["NanoArguAnaRetrieval"])
model = mteb.get_model("sentence-transformers/all-MiniLM-L6-v2")   # any mteb bi- or cross-encoder
results = mteb.evaluate(model, tasks=tasks)
```

Each view is its own task, so the task name in a results file says which one produced the score:

- `rcp.get_tasks()`: **reranking** over the judged pool (`NanoArguAnaRCPReranking`), the recommended setting.
- `rcp.get_tasks(view="retrieval")`: **open-corpus retrieval** (`NanoArguAnaRCPRetrieval`),
  bi-encoders only; see *Recommended use* below.

The same reranking tasks are in mteb itself once
[PR #5516](https://github.com/embeddings-benchmark/mteb/pull/5516) is merged.
When your mteb ships a task of the same name at the same data revision, `get_tasks()`
returns the built-in one, so the numbers are identical either way.

> **Renamed (October 2026).** Earlier versions of `rcp_ndcg_tasks.py` named the reranking tasks
> `…RCPRetrieval`. They are now `…RCPReranking`, like mteb's other reranking tasks, and
> `…RCPRetrieval` names the open-corpus view. Results computed with the earlier file under
> `…RCPRetrieval` names are reranking results; rename them to `…RCPReranking`. The earlier file
> also indexed only the pooled documents. That leaves dense-model scores unchanged but not those of
> models that use corpus statistics (e.g. BM25), so re-run those.

All 13 NanoBEIR tasks (mteb's `NanoBEIR` benchmark) are included, 649 queries in total. Each task has the judged
150-document candidate pool, calibrated relevance probabilities from an LLM judge, and full provenance.
Subsets are named after the mteb tasks (e.g. `NanoArguAnaRetrieval`), and the split is `train`, as in
mteb's Nano tasks.

**RCP-nDCG** (nDCG over *rubric-calibrated preferences*) replaces binary relevance labels with
calibrated relevance probabilities. An LLM judge compares pooled documents in a listwise tournament and
checks each one against a rubric of five binary relevance criteria. A 2PL item-response model then
calibrates those verdicts into a latent relevance `theta` per (query, document), and the relevance
probability `gain(theta)` is the gain in nDCG.

## ⚠️ Gains come from ONE judge: Qwen3.5-397B-A17B (NVFP4)

Every `gain` value comes from a single LLM judge, **Qwen3.5-397B-A17B (NVFP4 quantisation)**. The
judge answered five binary relevance criteria for each pooled document; a 2PL IRT model was fitted to
those answers and calibrated. The gain is the paper's `weighted_discrimination` link:

```
gain(θ) = Σ_k γ_k · σ(γ_k (θ − β_k)) / Σ_k γ_k        ∈ (0, 1)
```

- `item_params` for the gain are in `provenance/item_params.qwen35.json`.
- Every `gain` ships with its raw calibrated `theta`, so a different link can be applied without
  re-judging.
- Gains from a second judge (gpt-oss-120b) exist but are **not** included in this release.

## Recommended use: reranking

`{subset}-top_ranked` is the judged candidate list, and every candidate has a gain. Loaded through
mteb, a model reranks this list. This is the **recommended** setting:

- `ndcg_at_10`: standard nDCG over the upstream qrels (unchanged).
- `ndcg_float_at_10` (the main score): nDCG over the calibrated relevance probabilities, with linear
  gain. Documents tied on score are credited their tie group's mean gain.

**Open-corpus retrieval** works from the same data (`view="retrieval"`, tasks `…RCPRetrieval`): the
full upstream corpus is searched, minus each query's `excluded` documents (see *Evaluation protocol* below). The same metrics are reported, and the main score is
still `ndcg_float_at_10`, but it becomes a *pooled-judgment* score: gains exist only for the judged
pool, so a retrieved document outside it counts as gain 0. Compare open-corpus scores only with
each other, not with the reranking scores.

## Evaluation protocol

- **NanoArguAna excludes the query's own argument.** In ArguAna each query is itself an argument in the
  corpus, and BEIR/MTEB's full-size `ArguAnaRetrieval` drops it with `ignore_identical_ids`. Here the
  query's own argument is removed for **21 of 50** queries, from the candidates and from the ideal
  ranking: 20 share the query's id, and 1 is a byte-identical copy under another id
  (`test-religion-grcrgshwbr-pro03a` → `test-politics-grcrgshwbr-pro03a`), which `ignore_identical_ids`
  would miss. They are listed in `NanoArguAnaRetrieval-excluded` (`query-id`, `excluded-corpus-ids`),
  so the reranking and the full-corpus view both exclude them. No other Nano task has self-documents.
- **NanoNFCorpus is scored on the judged 150-document pools.** Four queries (PLAIN-1288, -1409, -2051,
  -1909) have more qrel positives than fit in 150; their judged pool is the top 150, and their other
  positives (667) lie outside `top_ranked`.
- **Human positives outside the pool** (the 667 NanoNFCorpus ones above and 7 NanoSCIDOCS documents that
  are empty upstream) keep their `score`, with `gain = 0.0` and `theta = null`.

## Layout

| config | columns | notes |
|---|---|---|
| `{subset}-corpus` | `id`, `title`, `text` | full upstream corpus at the pinned revision |
| `{subset}-queries` | `id`, `text` | |
| `{subset}-qrels` | `query-id`, `corpus-id`, `score`, `gain`, `theta` | `score`: upstream qrels, unchanged; `gain`: calibrated relevance probability (see below) |
| `{subset}-top_ranked` | `query-id`, `corpus-ids` | judged pool |
| `NanoArguAnaRetrieval-excluded` | `query-id`, `excluded-corpus-ids` | the query's own argument (see above) |
| `provenance-pool` | `query-id`, `corpus-id`, `pool_rank`, `rrf_score`, `gt_injected`, `excluded`, `judged` | split = subset |
| `provenance-runs` | `model`, `is_judge`, `query-id`, `corpus-id`, `score`, `rank_by_score`, `stored_position` | 14 rerankers + 2 judge strategies |
| `provenance-judge-criteria` | `query-id`, `call_index`, `corpus-id`, `C1`…`C5`, `finish_reason` | raw per-call criterion verdicts |

**Gains live in the qrels.** `{subset}-qrels` has one row per (query, document) in the judged pool,
plus any human-labelled document outside it:

- `score`: the human relevance label, unchanged (0 for pooled documents without a label).
- `gain`: the calibrated relevance probability, used by `ndcg_float_at_k`. It is 0.0 for the 674
  human-labelled documents outside the judged pool (see the evaluation protocol).
- `theta`: the raw calibrated latent relevance behind `gain`; null for those 674 unjudged rows.

Stock mteb reads only `query-id`, `corpus-id`, `score`. The extra score-0 rows change none of its
retrieval scores (verified on every published run). Two caveats:

- A `score` of 0 does **not** mean a human judged the document non-relevant. For the original human
  qrels, filter `score > 0`; for the judged pool, filter `theta` not null.
- Statistics that count "annotated" documents treat the judged pool as annotated. This affects mteb's
  descriptive statistic `unique_relevant_docs`, and trec_eval's `bpref` / judged@k.

Query instructions equal each mteb task's `prompt["query"]` (all 13 checked) and are applied by mteb,
so no `-instruction` config is shipped.

## How the pool was built

1. **First stage:** Cohere Embed v4, BM25 and
   [Octen-Embedding-8B](https://huggingface.co/Octen/Octen-Embedding-8B) are fused with unweighted RRF
   (`k = 60`), keeping the top 150 (`provenance-pool.rrf_score`). The component rankings were not kept
   for this suite, only their embeddings, so the fused pool is published.
2. **Ground-truth injection:** qrel positives missed by the fused top-150 were added. They are marked
   `gt_injected`, with `rrf_score = 0`.
3. **Judging:** a Stage A tournament, then Stage B pointwise binary criteria, then a 2PL fit.
   - Stage B rates every pooled document against five binary criteria (C1–C5), and a 2PL model is
     fitted to these verdicts.
   - The raw verdicts are in `provenance-judge-criteria`.

## Data notes

- **NanoNFCorpus pools.** The four deep queries' pools grew to 196–463 documents before judging; only
  the top 150 were judged, and those are the candidates here.
- `is_judge = true` runs in `provenance-runs` are the judge itself, not independent systems.

## Results: 14 rerankers under both tie rules

nDCG@10 in %, 649 queries over 13 datasets, each reranker scoring the 150-document candidate pool
(`top_ranked`). RCP-nDCG@10 uses the `gain` column with linear gain; its ideal ranking takes all gains of
the query. qrel-nDCG@10 uses the integer `score` with linear gain; its ideal ranking takes all positive
qrels. The two tie rules differ only in how documents with identical reranker scores are ordered:

- **(a)** breaks ties by document id (score descending, then corpus-id descending), the trec_eval /
  pytrec_eval convention and the rule of the paper's NanoBEIR table.
- **(b)** credits each tied document its tie group's mean gain, the expected nDCG over all orderings
  of the tie. mteb's `ndcg_float_at_k` uses this rule.

Mean is the unweighted mean over the 13 datasets. All numbers are replayed from `provenance-runs` at
revision `3462ee27487d585065756e7ea857082954bee8fb`.
